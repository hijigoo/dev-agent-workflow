GitHub Cloud Agent 기반 개발 업무 AX 전환

Jira 과업이 실제 GitHub Issue와 Copilot cloud agent의 개발·테스트·PR로 이어지고, 사람이 리뷰와 병합을 책임지는 전 과정을 회의실 예약 샘플로 검증합니다.

GitHub Enterprise Cloud FastAPI + React Jira Cloud + Local fallback 권장 180분
오프닝 멘트: 오늘의 목적은 AI가 코드를 잘 만드는지 단편적으로 보는 것이 아니라, 팀의 통제 가능한 개발 프로세스 안에서 한 명의 비동기 팀원처럼 일할 수 있는지를 확인하는 것입니다.

01 · Outcomes

세션이 끝나면 확인할 것

기능 시연보다 중요한 것은 추적성, 재현성, 사람의 승인, 실패 복구가 실제 팀 프로세스에 들어맞는지 확인하는 것입니다.

1업무 진입점

과업 표준화

Jira와 로컬 입력이 동일한 WorkItem 계약을 거쳐 GitHub Issue로 생성됩니다.

1실행 주체

Agent 위임

Issue에서 Copilot을 assignee로 지정하고 작업 세션과 PR을 추적합니다.

4품질 게이트

자동 검증

Lint, type check, test, build 결과를 PR에서 한 번에 검토합니다.

2사람의 관문

리뷰와 승인

보고자의 기능 리뷰와 독립 리뷰어의 코드 승인을 분리합니다.

성공의 정의

“Agent가 코드를 작성했다”가 아니라 “정의된 과업이 검증 가능한 변경으로 전환되고, 사람이 근거를 보고 안전하게 승인할 수 있다”입니다.

03 · Architecture

과업에서 병합까지

Jira는 업무 관리의 원본, GitHub는 개발 실행과 감사 추적의 원본입니다. 로컬 입력기는 Jira가 준비되지 않은 실습 환경만 대체합니다.

STEP 01과업 등록Jira Cloud 또는 로컬 Work Intake
STEP 02Issue 생성실제 GitHub 저장소, 원문 링크·인수 조건 포함
STEP 03Agent 할당GitHub UI에서 Copilot을 assignee로 지정
STEP 04개발·테스트격리된 Actions 환경에서 branch와 commit 생성
STEP 05PR·CI변경 근거, 테스트 결과, 제약사항 확인
STEP 06리뷰·재작업기능 검토 후 @copilot으로 수정 요청
STEP 07승인·동기화독립 승인 후 병합, Jira 상태 반영

자동화하는 영역

  • 과업 필드 정규화와 GitHub Issue 생성
  • branch, commit, PR 설명 생성
  • lint, type check, test, build 실행
  • PR·병합 상태를 Jira/로컬 화면에 반영

사람이 책임지는 영역

  • Agent-ready 과업 판정과 우선순위
  • 인수 조건의 업무적 타당성 확인
  • workflow 실행 승인과 민감 변경 검토
  • 독립 코드 승인 및 최종 병합 결정

Copilot 할당 방식

고객 시연의 기준 경로는 GitHub Issue 생성 후 GitHub UI에서 Copilot을 assignee로 지정하는 것입니다. API 자동 할당은 조직 정책과 현재 지원 범위를 사전 POC로 확인한 뒤 선택적으로 적용합니다.

05 · Sample issues

바로 등록할 샘플 과업

각 Issue는 작은 변경 범위, 검증 가능한 인수 조건, 명시적 제외 범위, 테스트 기대치를 포함합니다. 버튼으로 본문을 복사해 Jira 또는 GitHub에 사용할 수 있습니다.

[Feature] 수용 인원과 장비로 회의실 검색

agent-readyfeaturefrontendbackend
## 배경
사용자는 회의 참석 인원과 필요한 장비에 맞는 회의실을 빠르게 찾고 싶습니다.
현재는 전체 회의실 목록만 제공해 각 상세 화면을 하나씩 확인해야 합니다.

## 목표
회의실 목록 API와 화면에 최소 수용 인원 및 필수 장비 필터를 추가합니다.

## 요구사항
- 최소 수용 인원은 1 이상의 정수입니다.
- 장비는 `monitor`, `whiteboard`, `video` 중 복수 선택할 수 있습니다.
- 선택한 모든 장비를 보유한 회의실만 반환합니다.
- 필터가 없으면 기존 전체 목록 동작을 유지합니다.
- 검색 조건은 URL query string에 유지합니다.
- 결과가 없으면 빈 목록과 안내 문구를 표시합니다.

## 인수 조건
- [ ] `capacity=8`이면 수용 인원 8명 이상인 회의실만 조회된다.
- [ ] `equipment=monitor&equipment=video`이면 두 장비를 모두 가진 회의실만 조회된다.
- [ ] 잘못된 capacity는 HTTP 422와 이해 가능한 오류를 반환한다.
- [ ] 새로고침 후에도 검색 조건이 유지된다.
- [ ] API unit/integration test와 Web component test가 추가된다.
- [ ] 기존 예약 생성·조회 테스트가 모두 통과한다.

## 제외 범위
- 예약 가능 시간 검색
- 장비 관리 기능
- 검색 결과 정렬 및 페이지네이션
- 데이터베이스 종류 변경

## 구현 제약
- 기존 repository/service 분리를 유지합니다.
- 공개 API 응답 필드명을 변경하지 않습니다.
- 새로운 런타임 의존성 추가는 피하고 필요하면 PR에 이유를 설명합니다.

[Bug] 연속 예약의 경계 시각을 충돌로 판단

agent-readybugbackendregression
## 현상
기존 예약 종료 시각과 새 예약 시작 시각이 정확히 같을 때 예약 충돌로 처리됩니다.

## 재현 절차
1. 회의실 A에 2026-08-03 10:00~11:00 예약을 생성합니다.
2. 같은 회의실에 2026-08-03 11:00~12:00 예약을 생성합니다.
3. 두 번째 요청이 HTTP 409로 실패합니다.

## 기대 결과
종료 시각과 다음 시작 시각이 같은 연속 예약은 허용되어야 합니다.
실제 시간이 1분이라도 겹치는 예약은 계속 거부되어야 합니다.

## 인수 조건
- [ ] 10:00~11:00 다음의 11:00~12:00 예약이 성공한다.
- [ ] 10:00~11:00 예약이 있을 때 10:59~12:00은 HTTP 409로 실패한다.
- [ ] 동일한 시작 시각 또는 동일한 종료 시각의 중복 예약은 실패한다.
- [ ] 자정과 UTC 변환 경계에서도 같은 규칙이 적용된다.
- [ ] 실패를 먼저 재현하는 회귀 테스트가 추가된다.
- [ ] 기존 예약 테스트가 모두 통과한다.

## 조사 힌트
예약 구간을 반개방 구간 `[start, end)`로 취급해야 합니다.
현재 overlap 조건의 비교 연산자를 확인하세요.

## 제외 범위
- 반복 예약
- 시간대 정책 변경
- 예약 수정 기능 추가

[Test] 예약 충돌 API의 경계값 테스트 보강

agent-readytestquality
## 배경
예약 충돌 로직은 핵심 업무 규칙이지만 정상 경로 중심 테스트만 있습니다.
변경 없이 테스트 커버리지를 먼저 보강해 향후 리팩터링의 안전망을 만듭니다.

## 목표
예약 구간과 시간대 변환의 경계값을 검증하는 parameterized test를 추가합니다.

## 필수 테스트
- [ ] 완전히 동일한 시간 구간
- [ ] 기존 예약 내부에 포함되는 구간
- [ ] 기존 예약을 포함하는 구간
- [ ] 시작 부분이 겹치는 구간
- [ ] 종료 부분이 겹치는 구간
- [ ] 종료와 시작이 같은 연속 구간
- [ ] 서로 떨어진 구간
- [ ] KST 입력이 UTC 날짜 경계를 넘는 구간
- [ ] `end <= start` 입력 검증

## 제약
- production 코드는 변경하지 않습니다.
- 구현 세부사항이 아닌 API의 관찰 가능한 동작을 검증합니다.
- fixture와 factory는 기존 패턴을 재사용합니다.

## 완료 조건
- 전체 API test가 통과합니다.
- 새 테스트 이름만으로 실패 상황을 이해할 수 있습니다.
- 중복 setup을 helper 또는 parameterization으로 제거합니다.

PR 리뷰에서 Copilot에 보낼 후속 요청

reviewaccessibilityfollow-up
@copilot 검색 결과가 없을 때 현재는 빈 영역만 표시됩니다.

다음을 반영해 주세요.

1. `검색 조건에 맞는 회의실이 없습니다` 문구를 표시합니다.
2. 문구 영역에 `role="status"`를 적용해 스크린 리더가 결과 변경을 인지하게 합니다.
3. `검색 조건 초기화` 버튼을 추가하고 누르면 URL query string과 필터 UI를 함께 초기화합니다.
4. 빈 결과와 초기화 동작을 검증하는 component test를 추가합니다.
5. API와 기존 검색 테스트를 다시 실행하고 결과를 PR에 남겨 주세요.

범위를 넓혀 디자인 시스템이나 라우팅 구조는 변경하지 마세요.
설명 포인트: 좋은 Issue는 Copilot만을 위한 프롬프트가 아니라 사람 개발자에게도 좋은 업무 명세입니다. “어떻게 구현할지”보다 “어떤 행동을 검증할지”를 명확히 합니다.

06 · Test strategy

어떻게 테스트할 것인가

Agent의 자체 보고만 신뢰하지 않습니다. 변경 계층에 맞춘 자동 테스트와 사람이 확인하는 인수 시나리오를 PR의 병합 조건으로 사용합니다.

  2. 11:00~12:00 예약 성공을 확인합니다.
  3. 10:59~12:00 요청이 409인지 확인합니다.
  4. KST 입력과 UTC 저장값을 비교합니다.
  5. 전체 예약 테스트를 다시 실행합니다.

보여주지 말아야 할 잘못된 성공

Agent 댓글에 “테스트가 통과했습니다”라고 적힌 것만으로 완료 처리하지 않습니다. PR check의 실행 로그, 실제 테스트 수, 변경된 테스트 코드, 인수 시나리오 결과를 함께 확인합니다.

07 · Review & approval

리뷰에서 확인할 증거

보고자는 기능의 정합성을, 독립 리뷰어는 코드와 운영 위험을 확인합니다. Agent가 작성했다는 이유로 검토 기준을 낮추지 않습니다.

1. 과업 적합성

  • 인수 조건별 구현 근거
  • 제외 범위 준수
  • Issue와 PR 연결
  • 남은 제약의 명시

2. 변경 안전성

  • 변경 범위가 필요한 만큼만인지
  • 기존 구조와 패턴 재사용
  • 불필요한 의존성 추가 여부
  • 오류를 숨기는 fallback 여부

3. 검증 충분성

  • 실패를 재현하는 테스트
  • 경계값과 회귀 범위
  • 모든 필수 check 통과
  • 수동 인수 시나리오 완료

보고자 기능 리뷰

사용자 기대, 화면 문구, 업무 규칙, 인수 조건을 기준으로 검토하고 필요한 변경을 구체적인 관찰 가능 행동으로 요청합니다.

독립 리뷰어 승인

저장소 보호 규칙상 작업 시작자의 승인이 필수 승인 수에 포함되지 않을 수 있으므로 별도 reviewer를 지정합니다.

병합 직전 체크리스트
  • PR diff에 workflow, 권한, secret 관련 예상 밖 변경이 없다.
  • 모든 필수 check가 최신 commit에서 통과했다.
  • 리뷰 conversation이 모두 해결되었다.
  • 보고자의 기능 검토와 독립 reviewer 승인이 완료되었다.
  • 병합 후 Jira 상태와 릴리스 영향이 명확하다.

08 · Failure drills

실패했을 때도 통제되는가

고객에게 정상 경로만 보여주지 않습니다. 실패가 명확히 드러나고, 재시도와 사람 개입 지점이 정의되어 있는지를 함께 시연합니다.

차단 시연

CI 실패

의도적으로 실패하는 경계값 테스트를 확인하고, check 실패 상태에서는 병합 버튼이 차단됨을 보여줍니다.

복구: 실패 로그를 근거로 @copilot에 수정 요청 후 새 commit의 check를 다시 확인합니다.

차단 시연

권한 부족

GitHub App에 필요한 권한이 없을 때 Issue 생성 실패를 성공처럼 처리하지 않고 명확한 오류와 correlation ID를 표시합니다.

복구: 최소 권한만 추가한 뒤 같은 멱등성 키로 재시도합니다.

복구 시연

중복 webhook

같은 Jira 이벤트를 두 번 전송해도 GitHub Issue가 하나만 생성되는지 확인합니다.

증거: Jira key + repository 기반 idempotency record와 기존 Issue URL을 보여줍니다.

사람 개입

Agent 범위 이탈

Issue 범위를 넘어 구조 변경이나 dependency 추가가 발생하면 reviewer가 중단하고 작은 변경으로 되돌리도록 요청합니다.

복구: 제외 범위를 재강조하고 PR diff를 최소화합니다.

사람 승인

Actions 실행 대기

Copilot이 push한 PR workflow가 자동 실행되지 않는 정책에서는 사람이 변경을 먼저 검토합니다.

복구: workflow 변경 여부를 확인한 뒤 Approve and run workflows를 선택합니다.

병합 차단

필수 승인 부족

작업 시작자의 승인만으로는 ruleset의 필수 승인 수가 충족되지 않는 상황을 확인합니다.

복구: CODEOWNERS 또는 지정된 독립 reviewer의 승인을 요청합니다.

09 · Operating model

파일럿에서 팀 표준으로

초기에는 작고 검증 가능한 과업만 위임하고, 실패 데이터로 Issue template과 instructions를 개선한 뒤 범위를 넓힙니다.

WEEK 1

진단

정책, 라이선스, Actions, Jira 권한, 대상 저장소와 reviewer를 확정합니다.

WEEK 2

준비

샘플 저장소, instructions, setup steps, CI, ruleset, 연동을 구성합니다.

WEEK 3

파일럿

기능·버그·테스트 과업을 실행하고 lead time과 재작업을 측정합니다.

WEEK 4

표준화

Agent-ready 기준, 운영 절차, template, 예외·보안 정책을 팀 표준으로 확정합니다.

Agent-ready 과업

  • 변경 범위가 작고 독립적
  • 인수 조건을 테스트로 표현 가능
  • 운영 secret이나 민감 데이터 불필요
  • 기존 패턴과 참고 코드가 존재
  • 실패 시 rollback이 단순

초기 제외 과업

  • 운영 배포와 데이터 직접 변경
  • 인증·권한 모델의 대규모 변경
  • 요구가 불명확한 전면 재설계
  • 규제·개인정보 판단이 필요한 변경
  • 여러 저장소에 걸친 고위험 migration
