Cloud Agent 기반 플랫폼 개발·운영 자동화

Jira와 Slack을 업무 진입점으로 연결하고, 취약점 조치·E2E 테스트·신규 기능 개발·로그 기반 품질 진단을 GitHub 중심의 검증 가능한 흐름으로 전환합니다.

GitHub Enterprise CloudGitHub Copilot cloud agentGHASMini AgentAzure Container Apps권장 210분
테스트 앱 Work Intake
오프닝: Cloud Agent가 모든 것을 단독으로 자동화하는 그림이 아닙니다. 이벤트 감지와 반복 가능한 검증은 Actions, 코드 변경과 원인 분석은 Agent, 최종 판단과 병합은 사람이 담당하는 운영 모델을 보여드립니다.

03 · Common entry points

Jira로 할당하고 Slack으로 소통

외부 도구는 업무의 진입점과 알림 채널입니다. 코드 변경의 기록, 테스트, 리뷰, 승인은 GitHub에서 일관되게 관리합니다.

공식 연동

Jira → Cloud Agent

  1. Jira work item에 배경·인수 조건·대상 저장소를 작성
  2. Assignee를 GitHub Copilot로 지정하거나 @GitHub Copilot 호출
  3. Agent가 Jira 컨텍스트로 GitHub session과 PR 생성
  4. Jira activity에서 session·PR 링크 추적

필요: Jira AI/Rovo, Copilot for Jira 앱, GitHub App, repo write 권한

Public Preview

Slack ↔ Cloud Agent

  1. GitHub App DM 또는 thread에서 @GitHub Copilot 호출
  2. thread 컨텍스트를 바탕으로 작업 시작
  3. Slack에서 Agent 응답과 PR 링크 확인
  4. 세밀한 반복은 PR 댓글·Agents panel에서 진행

주의: thread 내용이 작업 컨텍스트로 저장될 수 있으므로 secret·개인정보를 전달하지 않습니다.

05 · Vulnerability remediation

GHAS 경고 발생 시 바로 조치

의존성 취약점과 코드 취약점은 생성 주체와 자동 조치 방식이 다릅니다. 하나의 “Cloud Agent 자동 수정”으로 뭉뚱그리지 않습니다.

GHAS native

Dependabot alert

  1. Dependency graph가 신규 취약점 탐지
  2. Dependabot security update가 최소 안전 버전 PR 생성
  3. 플랫폼 regression Actions 실행
  4. 실패 시 별도 Issue를 만들어 Cloud Agent에 호환성 수정 요청

핵심: 의존성 보안 PR의 기본 생성 주체는 Cloud Agent가 아니라 Dependabot입니다.

Agentic autofix

Code scanning alert

  1. CodeQL 경고 또는 Security campaign 생성
  2. 경고를 Copilot에 할당
  3. Agent가 코드베이스를 조사하고 수정·검증·draft PR 생성
  4. CodeQL clean과 regression checks 확인 후 보안 reviewer 승인

자동 배정: severity·CWE 정책에 따라 GitHub App/Actions가 API로 할당하는 별도 구현이 필요합니다.

02

보안 대응

탐지 후 PR까지 자동화하되 오탐 판단과 최종 위험 수용은 사람이 책임집니다.

PolicyCritical/High 즉시 작업, Medium batch campaign, 허용 CWE와 자동 할당 제외 경로 정의

Failure수정 불가·오탐·breaking dependency는 자동 병합하지 않고 Jira 보안 과업으로 escalation

06 · Test automation

UI와 에이전트 답변 품질 E2E

Cloud Agent가 브라우저를 탐색하는 데모와, 매 배포마다 반복되는 품질 게이트는 구분합니다. 반복 검증은 Actions의 고정된 test harness가 담당합니다.

결정론적 검증

응답 schema, citation 존재, tool 결과 일치, 금칙어, latency처럼 명확한 규칙을 우선합니다.

모델 기반 평가

정확성·유용성 평가는 rubric과 복수 샘플을 사용하고 사람 검토 없는 단독 병합 기준으로 쓰지 않습니다.

데이터 관리

운영 prompt 원문 대신 비식별·합성 dataset을 사용하고 버전·변경 사유를 Git으로 관리합니다.

신규 기능을 비동기로 병렬 개발

현실적 제약

한 Cloud Agent 작업은 한 저장소·한 브랜치·한 PR, 최대 59분입니다. 여러 저장소를 동시에 바꾸는 기능, 세션 간 공유 메모리, 충돌 없는 자동 통합은 별도 오케스트레이션과 사람 조정이 필요합니다.

08 · Quality monitoring

실제 로그에서 품질 저하 진단

GitHub가 플랫폼 런타임 로그를 자동 수집하지는 않습니다. 비식별 집계 파이프라인과 read-only 접근 경계를 먼저 만든 뒤 Agent가 분석합니다.

05

정기 진단

주간 품질 리포트와 개선 후보를 만들고, 승인된 항목만 코드 변경으로 전환합니다.

  • 분석 결과에서 원문 역추적 방지

09 · Sample issues

시연에 사용할 실제 과업 본문

각 본문은 복사해 Jira 또는 GitHub Issue에 사용할 수 있습니다. 범위, 인수 조건, regression, 제외 범위, 보고 형식을 명시합니다.

[Security] CodeQL High 경고 조치

## 배경
GHAS Code scanning에서 High severity 신규 경고가 검출되었습니다.

## 목표
경고 원인을 제거하고 CodeQL 재검사와 플랫폼 regression을 통과하는 최소 변경 PR을 만듭니다.

## 인수 조건
- [ ] 경고의 source-to-sink 경로와 악용 조건을 설명한다.
- [ ] 경고를 숨기거나 suppress하지 않고 근본 원인을 수정한다.
- [ ] 취약 동작을 재현하는 테스트 또는 방어 동작 테스트를 추가한다.
- [ ] CodeQL 재검사에서 대상 경고가 해소된다.
- [ ] unit/integration/E2E regression이 통과한다.
- [ ] 인증·권한·workflow·secret 변경이 있으면 별도 보안 검토를 표시한다.

## 제한
- unrelated refactoring 금지
- validation 제거 또는 broad catch 금지
- false positive로 판단하면 근거를 남기고 코드 변경 없이 보안 reviewer에게 escalation

## 승인
자동 병합하지 않습니다. Security CODEOWNER 승인이 필요합니다.

[Test] 에이전트 대화 핵심 E2E 자동화

## 목표
사용자 로그인부터 에이전트 응답과 tool 실행 결과 확인까지의 핵심 경로를 Playwright로 자동화합니다.

## 시나리오
1. 테스트 계정으로 로그인
2. 테스트 에이전트 선택
3. golden 질문 전송
4. streaming 응답 완료 대기
5. citation과 tool result 표시 확인
6. 새로고침 후 대화 이력 확인

## 인수 조건
- [ ] Chromium 기준 반복 실행이 가능하다.
- [ ] selector는 접근성 role/name을 우선 사용한다.
- [ ] 실패 시 screenshot, video, trace가 artifact로 저장된다.
- [ ] test data는 실행마다 격리되고 정리된다.
- [ ] secret과 실제 사용자 prompt가 artifact에 기록되지 않는다.
- [ ] GitHub Actions job summary에 pass/fail과 실행 시간이 표시된다.

## 후속
테스트 실패 원인을 제품 결함, 환경 결함, 비결정적 응답으로 분류해 리포트합니다.

[Feature] 대화 품질 리포트 다운로드

## 사용자 요구
운영자는 선택한 기간의 에이전트 품질 지표를 CSV로 다운로드하고 싶습니다.

## 범위
- 기간과 에이전트를 선택하는 UI
- 비식별 집계 API
- CSV 다운로드
- 권한 없는 사용자의 접근 차단

## 인수 조건
- [ ] 시작일·종료일·에이전트 필터가 적용된다.
- [ ] CSV에는 날짜, 성공률, fallback률, P95 latency, 평가 수만 포함된다.
- [ ] raw prompt, 사용자 ID, transcript는 포함되지 않는다.
- [ ] 기간은 최대 90일이며 잘못된 입력은 명확한 오류를 반환한다.
- [ ] API unit/integration, UI component, 핵심 E2E가 추가된다.
- [ ] 기존 품질 dashboard regression이 통과한다.

## 제외 범위
- 실시간 streaming export
- 원본 로그 다운로드
- PDF 리포트

## 보고
설계 선택, 개인정보 경계, 테스트 결과, 미해결 위험을 PR에 기록합니다.

[Analysis] 주간 에이전트 품질 저하 진단

## 입력
비식별·집계된 최근 7일 품질 데이터와 직전 4주 기준선

## 분석 항목
- task completion, fallback, tool error, no-answer 비율
- groundedness/citation score
- P50/P95 latency
- 사용자 평가와 escalation
- agent/version/channel별 편차

## 출력
1. 기준선 대비 유의미한 변화
2. 영향이 큰 실패 cluster 상위 5개
3. 가능한 원인과 근거 링크
4. 추가로 확인할 데이터
5. 개선 후보와 기대 효과
6. 개선 전후 검증할 E2E·품질 지표

## 제한
- raw prompt나 개인 식별 정보를 요청하거나 출력하지 않는다.
- 상관관계를 원인으로 단정하지 않는다.
- 근거 없는 코드 변경 PR을 만들지 않는다.
- 개선 제안은 Issue로만 등록하고 owner 승인 후 별도 구현한다.

## 완료 조건
GitHub Issue와 job summary에 동일한 리포트가 생성되고 입력 dataset 버전이 기록된다.

11 · Hands-on tutorial

처음부터 따라 하는 실행 튜토리얼

고객 환경에서 실제로 구성할 때의 순서입니다. 먼저 공통 기반을 완료한 뒤 필요한 시나리오 탭을 선택해 설정·실행·완료 증거를 확인합니다.

0. 공통 기반 준비

필수관리자 작업
1

조직 정책과 라이선스를 확인합니다

Enterprise 또는 Organization 설정에서 Copilot cloud agent 사용을 허용하고, 대상 사용자에게 유료 Copilot seat가 있는지 확인합니다. 대상 저장소가 cloud agent 사용에서 제외되어 있지 않아야 합니다.

Enterprise/Organization Settings → Copilot → Policies
2

저장소 보호 규칙을 설정합니다

기본 브랜치 직접 push를 막고 required checks, 최소 1명의 독립 승인, unresolved conversation 차단, CODEOWNERS를 설정합니다. 요청자의 승인이 필수 승인으로 인정되지 않을 수 있으므로 별도 reviewer를 지정합니다.

Repository Settings → Rules → Rulesets
3

Agent의 재현 가능한 환경을 만듭니다

기본 브랜치에 setup workflow를 먼저 병합해 Python·Node·시스템 도구와 잠금 파일 기반 의존성을 설치합니다. workflow job 이름은 반드시 copilot-setup-steps로 사용합니다.

.github/workflows/copilot-setup-steps.yml
jobs:
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
4

저장소 지침과 완료 조건을 기록합니다

아키텍처, 금지 변경, 테스트 명령, 민감 경로, PR 보고 형식을 적습니다. Agent가 추측하지 않도록 실제 실행 가능한 명령과 기대 결과를 사용합니다.

.github/copilot-instructions.md · .github/CODEOWNERS · PR template
5

기준 CI를 먼저 통과시킵니다

Agent를 할당하기 전에 기본 브랜치에서 lint, type, unit, integration, E2E, CodeQL이 정상 실행되는지 확인합니다. 기존에 실패하는 check를 Agent 작업의 실패로 오인하지 않도록 baseline을 보존합니다.

완료 증거: setup workflow 성공, required checks 목록, ruleset 화면, CODEOWNERS reviewer 자동 지정

1. Jira에서 Cloud Agent에 작업 할당

공식 연동
1

관리자가 Jira용 Copilot 연동을 설치합니다

Atlassian Marketplace의 GitHub Copilot for Jira 앱과 GitHub App을 설치하고 Jira AI/Rovo를 활성화합니다. GitHub App은 파일럿 저장소에만 접근하도록 범위를 제한합니다.

2

사용자가 GitHub 계정을 연결합니다

Jira에서 GitHub 인증과 조직 SSO를 완료하고 대상 저장소 write 권한을 확인합니다. 연결 테스트용 work item은 민감하지 않은 샘플을 사용합니다.

3

Agent-ready work item을 작성합니다

제목, 배경, 대상 저장소, 범위·제외 범위, 인수 조건, regression 명령, 보고 형식을 입력합니다. 이 문서의 “샘플 Issue” 본문을 그대로 사용할 수 있습니다.

4

GitHub Copilot에 할당합니다

Jira Assignee에서 GitHub Copilot을 선택하거나 댓글에 @GitHub Copilot을 호출합니다. Jira Automation을 사용할 때도 먼저 수동 흐름으로 권한과 컨텍스트 전달 범위를 검증합니다.

5

GitHub에서 결과를 검토합니다

Jira activity의 Agent session과 Draft/WIP PR에서 진행 상황을 확인합니다. Draft 중에는 01·02 job을 실행하지 않고, Agent가 Ready for review로 전환한 뒤 Actions checks를 시작합니다. 후속 수정은 Jira에서 새 작업을 만들기보다 기존 PR에 @copilot 댓글로 요청합니다.

완료 증거: Jira assignee/activity, Agent session, Ready for review PR, required checks, Jira의 최종 PR 링크

2. Slack에서 Agent와 커뮤니케이션

Public Preview
1

GitHub App for Slack을 설치합니다

Slack workspace 관리자가 GitHub 앱을 설치하고, 사용자가 개인 GitHub 계정·SSO를 연결합니다. 대상 private repository에 앱 접근이 허용되어야 합니다.

2

DM에서 기본 저장소를 설정합니다

GitHub App DM의 settings에서 파일럿 저장소를 선택합니다. 채널 전체 대화가 불필요하게 컨텍스트가 되지 않도록 첫 실습은 DM 또는 전용 비민감 thread에서 진행합니다.

3

작업을 요청합니다

대상 repo, 목표, 인수 조건, 제외 범위, 테스트를 포함해 @GitHub Copilot에 요청합니다. secret, 고객 prompt 원문, 운영 transcript는 입력하지 않습니다.

@GitHub Copilot platform-repo에서
          한국어 회의실 검색 intent 지원 PR을 만들어 주세요.
          Agent-ready Issue의 인수 조건과 regression을 따르고
자동 병합하지 마세요.
4

상태와 PR 링크를 확인합니다

Slack 응답의 session·PR 링크를 GitHub에서 열어 실제 로그와 checks를 확인합니다. Slack 메시지만 보고 완료 처리하지 않습니다.

5

후속 대화의 채널을 구분합니다

요청·상태 공유는 Slack, 코드 라인별 수정은 PR review, 장기 추적은 Jira를 사용합니다. 전체 thread가 작업 컨텍스트로 저장될 수 있음을 참가자에게 알립니다.

완료 증거: Slack 요청·응답, GitHub session, PR checks, PR review 댓글

3. GHAS 신규 취약점 조치

DependabotCode scanning Agent
1

GHAS 탐지 기능을 활성화합니다

Dependency graph, Dependabot alerts·security updates, CodeQL default 또는 advanced setup, secret scanning을 활성화합니다. required checks에는 CodeQL과 dependency review를 포함합니다.

Repository Settings → Security & analysis
2

의존성 경고는 Dependabot PR로 처리합니다

Dependabot security update PR에서 안전 버전 diff와 compatibility를 확인하고 플랫폼 regression을 실행합니다. 테스트 실패로 추가 코드 수정이 필요할 때만 별도 Issue를 만들어 Cloud Agent에 할당합니다.

3

CodeQL 경고를 Copilot에 할당합니다

Security 탭의 개별 Code scanning alert 또는 Security campaign에서 Assign to Copilot을 선택합니다. 초기에는 High severity 샘플 한 건으로 권한·수정·PR 흐름을 검증합니다.

4

자동 할당 정책은 별도로 구현합니다

기본 trigger가 모든 신규 보안 경고를 자동 할당하지는 않습니다. GitHub App 또는 scheduled Actions가 severity, CWE, 경로, 제외 목록을 평가한 뒤 API로 Copilot assignee를 지정하게 합니다.

5

보안 증거를 검토합니다

경고를 suppress하지 않았는지, source-to-sink와 악용 조건을 설명했는지, CodeQL clean과 regression이 통과했는지 확인합니다. 오탐과 위험 수용은 Security reviewer만 결정합니다.

완료 증거: alert before/after, Agent draft PR, 재현 test, CodeQL clean, Security CODEOWNER 승인

핵심 사용자 경로를 먼저 선정합니다

apps/web/tests/e2e · playwright.config.ts · .github/workflows/ci.yml
npx playwright test

답변 품질 dataset과 rubric을 버전 관리합니다

비식별 synthetic/golden 질문에 기대 citation, tool 사용, 필수 사실, 금지 응답을 정의합니다. 정확성·groundedness·안전성·tool 성공률·latency threshold를 코드 리뷰로 변경하게 합니다.

tests/quality/dataset.jsonl · tests/quality/rubric.yml

PR에서는 작은 smoke set, nightly에서는 전체 browser·dataset matrix를 실행합니다. threshold 미달은 check 실패와 job summary annotation으로 표시합니다.

실패를 Agent 작업으로 전환합니다

workflow가 report와 artifact 링크를 포함한 Issue를 생성하면 Test Agent가 재현·원인 분석·수정 PR을 만듭니다. Agent는 golden answer나 threshold를 임의로 낮추지 못하게 CODEOWNERS로 보호합니다.

완료 증거: PR check, Playwright report·trace, quality scorecard, 실패 Issue, 수정 전후 비교

5. 로그 기반 주간 품질 모니터링

별도 구현MCP 선택
1

비식별 집계 계약을 먼저 정의합니다

날짜, agent/version/channel, task 성공률, fallback, tool 오류, no-answer, groundedness, latency, 평가 수만 제공합니다. raw prompt, transcript, 전화번호, 사용자 ID는 제외합니다.

schemas/quality-metrics.schema.json
2

read-only 데이터 접근을 만듭니다

권장 방식은 Actions가 로그 플랫폼 API에서 집계 데이터만 가져오는 것입니다. MCP를 사용한다면 read-only tool, 최소 secret, firewall allowlist와 감사 로그를 적용합니다.

3

주간 분석 workflow를 예약합니다

Actions schedule이 최근 7일과 직전 4주 기준선을 내려받고 schema·비식별 검사를 통과한 데이터만 분석 작업에 전달합니다. 동일 기간의 중복 리포트 생성을 막습니다.

.github/workflows/weekly-quality-review.yml
4

Agent 분석 출력 형식을 고정합니다

변화량, 영향이 큰 실패 cluster, 근거 링크, 가능한 원인, 추가 확인 데이터, 개선 후보, 검증 지표를 Issue template에 맞춰 작성합니다. 상관관계를 원인으로 단정하지 않게 지시합니다.

5

개선 제안과 코드 변경을 분리합니다

주간 분석은 보고 Issue까지만 생성합니다. 운영 owner가 채택한 개선안만 별도 Jira/GitHub Issue로 만들고 Cloud Agent가 구현·E2E·전후 비교 PR을 수행합니다.

완료 증거: dataset version, 비식별 검사, weekly job summary, 품질 Issue, 승인된 개선 Issue, 전후 scorecard

6. 평가·승인 후 Azure Container Apps 배포

GitHub Actions운영 승인
1

Azure와 GitHub를 secret 없이 연결합니다

Azure Entra application에 GitHub OIDC federated credential을 만들고 subject를 GitHub API가 반환한 immutable repository prefix와 :environment:production 조합으로 제한합니다. 대상 resource group에서만 Contributor와 User Access Administrator를 부여합니다.

docs/azure-container-apps-deployment.md
2

production Environment를 보호합니다

GitHub Environment에 required reviewer를 지정하고 Azure client·tenant·subscription ID는 Environment secrets로, location·resource group·name prefix는 variables로 저장합니다. 승인 전 job은 이 값에 접근할 수 없습니다.

Repository Settings → Environments → production
3

병합된 commit을 다시 평가합니다

main push에서 Python·Web·Playwright·비식별 품질 scorecard를 실행합니다. PR 시점 결과가 아니라 실제 병합 commit SHA의 artifact를 배포 승인 근거로 사용합니다.

.github/workflows/deploy-aca.yml
4

평가 후 운영 승인을 기다립니다

평가가 성공해야 deploy job이 생성되고 production reviewer 승인을 기다립니다. 승인 전에는 Azure login, Bicep, ACR build가 실행되지 않습니다. PR 병합 승인과 운영 배포 승인을 분리합니다.

5

불변 image와 독립 URL을 확인합니다

승인 후 OIDC 로그인, ACR의 commit SHA image build와 세 ACA revision 배포가 실행됩니다. 테스트 앱은 회의실·Mini Agent만 제공하고, Work Intake는 업무 요청·Issue 생성만 제공합니다.

Health: 테스트 앱 · Meeting API · Work Intake

완료 증거: post-merge artifact, Environment approval audit, OIDC login, SHA image, ACA revision과 두 외부 URL

진행 팁: Agent가 라이브로 일하는 동안 Jira·Slack 연동 구조와 안전장치를 설명하고, 결과 검토는 같은 시나리오로 미리 준비한 PR을 사용합니다.

13 · Guardrails & rollout

자동 생성과 자동 병합을 분리

초기 파일럿은 분석·PR 생성까지 자동화하고, Actions 실행·오탐 판단·보안 검토·최종 병합은 사람이 담당합니다.

사람 승인

PR·Actions

Copilot PR workflow는 정책에 따라 Approve and run workflows가 필요하며 Agent는 PR을 승인·병합하지 않습니다.

데이터 경계

Jira·Slack·로그

외부 thread와 session log의 노출 범위를 설명하고 secret·개인정보·raw transcript를 전달하지 않습니다.

비용·한도

실행 자원
