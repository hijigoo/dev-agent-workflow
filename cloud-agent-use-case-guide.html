Cloud Agent Setup

Agent job 내부에서 Python·Node·의존성을 재현 가능하게 준비합니다.

01

PR Validation

Ready 전환 시 품질 검증 후 CodeQL을 실행합니다. 후속 commit은 PR branch로 수동 재실행합니다.

02

Production Deployment

Main 재평가 후 배포 flag가 true일 때만 승인 알림·Production 승인·ACA 배포를 실행합니다.

03

Optional Review

주간 CodeQL과 수동 비식별 품질 리포트를 분리해 실행합니다.

Common requirements

1. 작업 할당과 커뮤니케이션

1
답변: Jira·GitHub Issue에서 구조화된 과업을 만들고 Copilot에 할당할 수 있습니다. Slack은 요청·상태 확인 채널로 사용할 수 있지만, 코드별 수정·승인 기록은 GitHub PR을 기준으로 유지해야 합니다.
Jira 연계GitHub Issue

권장 할당 프로세스

  1. Jira work item에 목표, 대상 repository, 범위, 제외 범위, 검증 명령을 기록합니다.
  2. Jira 연동 또는 GitHub UI가 추적 가능한 GitHub Issue를 생성합니다.
  3. GitHub UI에서 Copilot을 assignee로 지정합니다. tenant 정책이 허용하는 경우 API routing을 추가합니다.
  4. Cloud Agent session·branch·Draft PR 링크를 Jira activity에 되돌려 기록합니다.
  5. 사람이 Ready for review로 전환한 뒤 01 workflow와 독립 리뷰를 시작합니다.
Slack 연계PR이 기준 채널

커뮤니케이션 채널 분리

  • Jira: 요구사항, 우선순위, 담당자, 장기 상태 추적
  • Slack: 비민감 요청, 진행 상태, session·PR 링크 공유
  • GitHub Issue: Agent가 실행할 정규화된 작업 계약
  • GitHub PR: 코드 라인별 feedback, @copilot 후속 수정, 승인
  • Actions: 테스트·CodeQL·artifact·배포 승인 증거
Slack thread 전체나 Jira 첨부물을 무조건 Agent context로 넘기지 않습니다. secret, 고객 원문, 개인정보는 제거하고 필요한 사실만 Issue에 정리합니다.

Open-source upgrades

2. Dograh·Pipecat 버전 업그레이드

2
답변: 가능합니다. 다만 “신규 릴리즈 발견 즉시 운영 반영”이 아니라 릴리즈 감지 → upgrade Issue → Agent PR → regression → 사람 Merge로 통제해야 합니다. 현재 저장소에는 release watcher가 없으므로 추가 구현 항목입니다.
추가 구현

권장 release watcher

  1. GitHub Releases API를 매일 또는 주 2~3회 조회합니다.
  2. 현재 pinned version과 최신 stable tag를 비교하고 pre-release는 정책에 따라 제외합니다.
  3. 새 tag마다 중복 방지 marker가 있는 Agent-ready Issue를 하나만 생성합니다.
  4. changelog·migration·dependency diff·영향 경로를 Issue에 첨부합니다.
  5. 한 PR에서 Dograh와 Pipecat을 동시에 올리지 않고 upstream별로 분리합니다.

Feature delivery

5. 신규 기능 개발

5
답변: 요구사항을 Agent-ready Issue로 전달하면 Cloud Agent가 비동기로 구현·테스트·Draft PR까지 수행할 수 있습니다. 사람은 여러 session을 직접 코딩하는 대신 범위 설정, Ready 전환, 리뷰, Merge와 배포 승인에 집중합니다.

좋은 Agent-ready 요구사항

  • 사용자 문제와 기대 동작
  • 대상 repository·서비스·관련 파일
  • 포함 범위와 명시적 제외 범위
  • 재현 방법과 실행할 검증 명령
  • API·보안·개인정보·호환성 제약
  • PR 보고 형식과 자동 merge 금지

병렬 처리 운영 원칙

  • 한 Issue는 한 repository·한 PR 크기로 제한
  • 공유 API contract 변경은 기술 리드가 먼저 확정
  • 서로 의존하는 작업은 dependency 순서를 명시
  • 같은 파일을 동시에 바꾸는 session 수를 제한
  • 각 Agent는 자신의 branch와 PR만 변경
  • 사람 reviewer capacity를 WIP limit로 사용

Decision FAQ

도입 전에 합의할 질문

각 자동화의 성공 조건과 예외 처리 책임자를 먼저 정해야 Agent가 팀원처럼 예측 가능하게 동작합니다.

Cloud Agent가 직접 Merge하거나 Production 배포까지 자동 승인해도 되나요?
권장하지 않습니다. 현재 workflow도 Issue 또는 PR까지 자동화하고, Merge와 Production Environment 승인을 사람에게 남깁니다.
왜 Draft에서는 PR Validation run을 만들지 않나요?
Agent 작업 중 commit마다 Skipped check가 누적되는 화면 noise를 없애기 위해 ready_for_review 이벤트에서만 01 workflow를 시작합니다. Ready 이후 commit은 PR head branch로 수동 재실행합니다.
Main 2/3·3/3이 Skipped되면 실패인가요?
아닙니다. ACA_DEPLOYMENT_ENABLED=false인 안전 상태에서는 의도된 결과입니다. 실제 배포 시 true로 변경하고 02 workflow를 main에서 실행합니다.
업그레이드와 취약점 수정은 완전 무인화할 수 있나요?
감지·Issue·Agent PR·regression은 자동화할 수 있습니다. breaking change, 보안 위험 수용, Merge와 운영 배포는 사람 승인이 필요합니다.
